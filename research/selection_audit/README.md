# Crypto alert-selection audit — 2026-10-05

Engineering only. No deployment, thresholds, screening policy, model training, paid calls or live execution changes. Existing collection continues.

Purpose: establish whether the retained historical data can support an ALERT-versus-comparable-unalerted diagnostic, and examine pre-alert extension and outcome missingness. This is a feasibility and exploratory audit, not independent predictive validation.

The owner-run exporter opens the protected production database with SQLite mode=ro and query_only, in one read transaction. It reads ledger activation metadata only and restricts ALERT/SHADOW cases to those whose entire six-hour follow-up and lateness allowance ended before activation. It never reads live ledger predictions, probabilities, results or excluded identities. Only whitelisted numerical features and historical outcome/coverage columns are exported; no company, conversation, credential or wallet runtime payloads. The private export is outside the git checkout, mode 0600, in a directory mode 0700 owned by vivameda-engineer. Existing exports are preserved. No service restarts or provider requests.

The audit selects the first retained ALERT per mint without substituting later cases when an endpoint is missing. Controls must pass basic scanner eligibility, be observed in the preceding five minutes, have the same regime, and have market cap and liquidity within a factor of two. Matching uses no outcome. Previously alerted and same-token controls are refused; controls that alert later remain eligible at index time. Control reuse is explicit. All matched pairs are selected before outcome coverage is examined. Primary historical diagnostic: 60-minute endpoint multiple, paired difference and endpoint >=2x counts. Three- and six-hour endpoints are secondary descriptions. All endpoint analyses require exact timing, lateness <=180 seconds, matching horizon-metric timestamps and complete path coverage with maximum gap <=180 seconds. Missing/incomplete outcomes are not losses. No global/lifetime peak labels or trade P&L.

Important limitation: stored SHADOW cases are first observations, not a complete contemporaneous eligible candidate universe. Token-age matching is unavailable in this scoped export. Reconstructed features need not equal emitted inputs. Controls and alerts have different observation times, and complete-pair selection can be biased. No significance interval or scanner-edge verdict is produced from these matches. Zero or few comparable controls means this dataset cannot answer the question adequately; it is not evidence the scanner is good or bad.

Next decision after the historical audit: prepare a separate dated forward candidate/control capture protocol with exact index-time eligibility, token age, common market/time windows, immutable decision inputs, identical follow-up and missingness reporting. Avoid matching away the score's predictive features. Freeze sample-size/stopping and day-cluster inference before new outcomes. Any necessary instrumentation remains subject to source review and normal deployment; no new collector is deployed by this audit.

The current model ledger retains its original specification and stop. At baseline 3/42, 200 eligible tokens gives 14.29 expected positives; requiring at least 20 positives and 20 decision days can yield inconclusive results. Merely increasing the sample to about 280 achieves an expectation of 20 positives, not adequate power. A revised protocol requires a separate dated rationale and disclosure of prior inspections, not retrospective alteration or an outcome-driven extension.
